## Current implementation notes

Port `8765` had no listener (`ERR_CONNECTION_REFUSED`); a prior server session also logged HTTP 503 because it targeted a nonexistent feature-test schema. This was an environment/server lifecycle and DB-target issue, not a React API-base-path defect. Before opportunistic pumping was disabled in the temporary router, one queued fixture webhook job was observed entering its retry path; the existing test schema was not reset or dropped. The server remains available at `http://127.0.0.1:8765/`; the test-only router now disables opportunistic background-job pumping to avoid further queue changes from browser requests.
- **Inbound receipt-to-UI evidence (2026-10-17):** Against isolated MariaDB schema `anibros_crm_feature_tests_20261017_workerrecover2`, the original compiled React UI at `http://127.0.0.1:8766/leads` submitted website events through the PHP receiver (HTTP 200, `accepted: 1`). The PHP processor persisted a unique lead (`status=created`, non-null `lead_id`), and the same Leads page rendered it with no load error; its `/api/v1/leads` request returned HTTP 200. A second event matching an existing open lead was correctly marked `duplicate` and linked to that lead. `Receiver.php` logged persistence transaction durations of 6.638, 6.779, and 6.906 ms for three receipts. For the distinct lead, `processed_at=2026-10-17 02:29:56.413 UTC` and browser visibility was observed at epoch `1792204206173` (9.760 s later). That interval includes manually invoked processing and browser-test orchestration; it is one local sample, not an intrinsic delivery delay or production SLO. `tests/inbound_contract.php` passed after adding the instrumentation. The temporary `:8766` process is stopped after verification; the existing `:8765` server is retained.
- **Actual scheduled-worker path (2026-10-17):** A fresh additive schema `anibros_crm_feature_tests_20261017_asyncworker1` was migrated; no existing schema was altered/reset. A browser POST to its website endpoint returned HTTP 200 in 85 ms. The committed event/job were present before processing (`received_at=02:47:13.433 UTC`, queued job created at `02:47:13.437 UTC`; receiver log at `02:47:13.440 UTC` recorded `persistMs=9.72`). The test router sets `pump_after_response=false`, but `Config` defaults to `true` and the standalone production worker entry point is independent of that switch. A timer launched `bin/worker.php` at the next UTC minute boundary (`02:48:00.872 UTC`); its actual output was `{"claimed":1,"succeeded":1,"retried":0,"dead":0}`. The event became `created` with `lead_id` at `02:48:01.038 UTC`, the lead row was inserted at `02:48:01.016 UTC`, and the already-open React Leads page invalidated from realtime polling and displayed it at `02:48:06.321 UTC` after an HTTP 200 `/api/v1/leads` request. Thus this single measured sample was 47.583 s receipt-to-lead persistence, 47.605 s receipt-to-event completion, and 52.888 s receipt-to-browser visibility; event/job persistence itself took 9.72 ms. This is a cron-equivalent timer around the real CLI worker, not an installed OS crontab or cPanel test. A once-per-minute cron inherently leaves a potential near-60-second queue wait; the local test does not prove a seconds-level cPanel SLO. The screenshot's stopped `:8766` service was restored for the run; `/tasks` rendered and both task APIs returned HTTP 200.
- **Worker reliability checks (2026-10-17):** Two concurrent POSTs with the same endpoint/event ID both received the receiver's normal HTTP 200 acknowledgement; MariaDB contained exactly one inbound event, one inbound job and one resulting lead. A stale final-attempt lease simulated an interrupted worker; after correcting the fixture to use UTC (the CLI mysql client defaulted to local time while PHP PDO deliberately uses UTC), `bin/worker.php` reaped the job to `dead` and `InboundProcessor::reconcileDeadJobs()` marked the event `failed` with a visible recovery reason. The actual authenticated retry API returned HTTP 201; the next actual worker run created the lead. For worker concurrency, 12 attempted website submissions yielded 8 accepted and 4 explicitly rejected with HTTP 429 by the source's configured rate limiter; all 8 accepted events were processed exactly once. Two `bin/worker.php` processes started 21 ms apart and claimed 5 and 3 jobs respectively; all eight event jobs finished and eight distinct leads appeared in the live-polling Leads page. A signed local outbound receiver also returned HTTP 503; the actual worker persisted a queued retry and logged the retry delay. After changing only the isolated fixture endpoint to return HTTP 200 and making the retry due, the worker completed that delivery on attempt two. These are local MariaDB/local-receiver tests, not live provider or cPanel tests. The isolated browser/API server on `:8766` remains running against this new test schema; the existing `:8765` server was left untouched.
- **Shared-host scheduling limit:** `bin/install.php` and the project deployment notes prescribe `* * * * * .../bin/worker.php`; `bin/worker.php` itself is bounded to a 55-second pump and up to 100 jobs. With cron alone, delivery within seconds is not guaranteed; the local actual-worker sample waited 47.439 s for the next minute boundary. Production config enables an opportunistic post-response pump with an 8-second budget, but its behavior under the intended cPanel PHP/FPM setup has not been demonstrated. No authorized cPanel account or live provider credentials are available.
